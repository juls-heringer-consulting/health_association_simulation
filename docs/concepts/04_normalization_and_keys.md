# 04 Normalisation, keys and constraints

*Phase 3 (core). Scripts: `sql/30_core`, `sql/40_core_load`.*

## Normalisation in three sentences

Store every fact **once**, in the table where it belongs, and connect tables by keys.
Redundancy is dangerous because copies drift apart (the practice address in 3,000 billing
rows, one of them updated). Normal forms are the checklist.

| Normal form | Rule | Violation in the sources | Fixed in core |
|---|---|---|---|
| **1NF** | one value per cell, no lists | Excel cell `Fachgruppenschluessel = "01, 03"`, `Kreise_AGS = "10041, 10042, ..."` | `STRING_SPLIT` → one row per value in `core.fachgruppe.arztgruppe_code`, `core.planungsbereich_kreis` |
| **2NF** | in a table with a composite key, every column depends on the *whole* key | a billing line row repeating the practice name (depends only on the case, not on the line) | practice data lives in `core.praxis`, the line only has `fall_id` |
| **3NF** | no column depends on another non-key column | EBM: chapter title stored with every GOP (depends on the chapter number, not the GOP) | `core.ebm_kapitel` holds the title once; `core.gop.kapitel_nr` is a foreign key |

Deliberate exception: `core.leistung.punktzahl` (DD-06 in [design_decisions.md](../design_decisions.md)).

## Keys

| Kind | Meaning | Example |
|---|---|---|
| **Business (natural) key** | identifies a thing in the real world | LANR, BSNR, IK, AGS, Aktenzeichen |
| **Surrogate key** | meaningless number generated by the database | `arzt_id INT IDENTITY` |
| **Composite key** | several columns together | `teilnahme_status (teilnahme_id, valid_from)` |
| **Foreign key** | column that must match a key of another table | `teilnahme.arzt_id → arzt.arzt_id` |

Rule in this project (DD-03): entities get a surrogate primary key **and** a UNIQUE
constraint on the business key. The surrogate makes joins fast and stable; the UNIQUE
constraint makes sure a LANR exists only once.

**Many-to-many**: a doctor works at several practices over time, a practice has several
doctors. A relational database solves this with an *associative table* - `core.teilnahme` -
which also carries the attributes of the relationship (form, Anrechnungsfaktor, validity).

## Constraints: let the database enforce the rules

| Constraint | Example | What it prevents |
|---|---|---|
| `PRIMARY KEY` | `pk_arzt` | duplicates, NULL keys |
| `FOREIGN KEY` | `fk_leistung_gop` | billing lines with a GOP that does not exist |
| `UNIQUE` | `uq_abrechnungsfall_patient (praxis_id, quartal_code, patient_pseudonym)` | two cases for the same patient, practice and quarter (definition of a Behandlungsfall!) |
| `CHECK` (one column) | `ck_teilnahme_faktor IN (0.25, 0.5, 0.75, 1.0)` | invalid values |
| `CHECK` (several columns) | `ck_arzt_lanr_fachgruppe: RIGHT(lanr, 2) = fachgruppe_code` | LANR and Fachgruppe contradicting each other |
| `CHECK` (business rule) | `ck_honorarbescheid_punkte: angefordert = berichtigt + mgv + egv` | a Bescheid that does not add up |
| `DEFAULT` | `df_teilnahme_valid_to = '9999-12-31'` | forgotten values |
| filtered `UNIQUE INDEX` | `uq_teilnahme_status_open ... WHERE valid_to = '9999-12-31'` | two "current" statuses |
| exclusive arc `CHECK` | `ck_dokument_bezug_genau_ein_ziel` | a link pointing to two things or nothing |

Constraints are documentation that cannot lie: if the data violates them, the load fails.

## Data types

| Data | Type | Why |
|---|---|---|
| codes and numbers you don't calculate with | `CHAR(n)` / `VARCHAR(n)` | leading zeros, check digits (LANR, AGS, GOP) |
| names, texts with umlauts | `NVARCHAR(n)` | Unicode |
| money | `DECIMAL(12,2)` | exact; never `FLOAT` for money |
| dates | `DATE`; time stamps `DATETIME2(0)`; with UTC offset `DATETIMEOFFSET(0)` | precision as needed |
| flags | `BIT` | |

## Try it

```sql
-- the constraint protects you: this fails with a CHECK violation
INSERT INTO core.teilnahme (arzt_id, praxis_id, teilnahmeform_code, anrechnungsfaktor, valid_from)
VALUES (1, 1, 'ZUL', 0.3, '2025-01-01');

-- list all constraints of a table
SELECT name, type_desc FROM sys.objects WHERE parent_object_id = OBJECT_ID('core.abrechnungsfall');
```

In SSMS: right-click `core.teilnahme` → Design, or create a database diagram
(Database Diagrams → New) with arzt, praxis, teilnahme to see the many-to-many.
